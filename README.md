# minillm

A 152M-parameter language model trained end-to-end: pretraining, supervised finetuning, and RL with verifiable rewards,
in pure PyTorch on a single consumer GPU (mine is an 11GB RTX 2080 Ti).

The goal of this project is to implement and understand the different stages of the modern LLM training stack, at a
scale where one person with one GPU can iterate quickly. All code here is written by hand - the point of the project is
to internalize the details, not to get it to run as quickly as possible.

## Highlights

- **Llama-style architecture from scratch**: RoPE, SwiGLU, RMSNorm, grouped-query attention
- **Batched inference engine** with simple KV caching and support for left/right padding
- **Full training pipeline**: mixed-precision (fp16) training, gradient accumulation, chunked cross-entropy loss
- **Three-stage training on GSM (grade school math)**: FineWeb pretraining → SFT on TinyGSM (46.5% pass@1)→ GRPO on GSM8K (53.9% pass@1)

## How to run

```bash
# install uv (https://docs.astral.sh/uv/getting-started/installation/)

# Pretrain
uv run main.py pretrain --dataset fineweb-sample

# Finetune on TinyGSM
uv run main.py gsm_sft --pretrained_model_path <path to pretrained model>

# GRPO on GSM8k
uv run main.py gsm_grpo --model_path <path to finetuned model>

# Eval on GSM8k
uv run main.py gsm_eval --model_path <path to model> --eval_greedy <True/False> --eval_top_p <an integer or omit>

# Run inference on a given input
uv run main.py infer "What is 2 plus 2?" --model_path <path to model>
```

## Architecture & implementation notes

**Model** (~152M params): 12 transformer blocks, 768 model dim, pre-norm residual layout with RMSNorm, SwiGLU FFN (2048
hidden, fused gate+value projection), RoPE (theta=10000, precomputed sin/cos buffers), 1024 max context. The tokenizer is
GPT-2 BPE via `tiktoken`; the vocabulary is padded up to a multiple of 64 (50304) for tensor-core-friendly matmul
shapes. Embedding and LM head are untied. Init follows GPT-2: std 0.02 everywhere, with residual output projections
scaled by 1/sqrt(2 \* num_layers).

**Attention.** Grouped-query attention with 12 query / 4 KV heads with some quirks due to the older GPU:

- Turing GPUs have no flash attention kernel, so attention runs through SDPA's `EFFICIENT_ATTENTION` backend. Slower
  than flash, but still drops attention memory from quadratic to linear in sequence length: **2736 MB → 218
  MB** at batch size 4, which allowed raising the batch size from 4 to 10
- `EFFICIENT_ATTENTION` doesn't support the `enable_gqa` flag, so K/V are expanded to the query-head count via
  `repeat_interleave` before being written to the KV cache. The expansion
  happens once per token as it's written into the cache, instead of re-expanding the entire cached K/V at every decode step.

**Batched inference.** Static pre-allocated KV cache. The attention bias is built manually each step (causal mask from
`input_pos` + padding mask), including a guard for left-padded batches: pad tokens attend to themselves so their
attention rows aren't all −inf, which would produce NaNs after softmax.

**Training memory.** The full-vocab logit tensor was the peak-memory bottleneck (batch × seq × 50304 logits in fp32+fp16
≈ 3 GB at batch size 10). The loss is computed in chunks along the sequence axis with activation checkpointing, so the LM
head is recomputed per-chunk in the backward pass - peak memory drops ~N× for N chunks at a small compute cost, raising
the max batch size from 10 to 16 (see `chunked_cross_entropy_loss` and `chunked_log_probs`).

## GSM8K (Grade School Math) experiments

[GSM8K](https://github.com/openai/grade-school-math) is a benchmark of grade-school math word problems requiring 2–8
steps of arithmetic reasoning. The model is trained to produce a small Python program that would return the correct
answer for the math problem (Program of Thoughts style). The task is hard enough for a small model and it has a
verifiable final answer - which makes it suitable for RLVR.

**Example problem:**

> Julie is reading a 120-page book. Yesterday, she was able to read 12 pages and today, she read twice as many pages as
> yesterday. If she wants to read half of the remaining pages tomorrow, how many pages should she read?

**minillm's output** (after GRPO, with empty lines omitted for brevity):

```python
def simple_math_problem() -> int:
    total_pages = 120
    pages_read_yesterday = 12
    pages_read_today = 2 * pages_read_yesterday
    remaining_pages = total_pages - (pages_read_yesterday + pages_read_today)
    pages_to_read_tomorrow = remaining_pages / 2
    result = pages_to_read_tomorrow
    return result
```

### Stage 1: SFT on TinyGSM ([HF logs](https://huggingface.co/chibo/minillm/tensorboard))

The pretrained model is finetuned on [TinyGSM](https://arxiv.org/abs/2312.09241), a synthetic dataset of GSM8K-style
problems generated by LLMs, for one epoch (11.8M samples).

**Hyperparameters** deliberately mirror the TinyGSM paper where possible: effective batch size 1024 (micro-batch 16 \*
64 gradient-accumulation steps), peak LR 1e-4, weight decay 0.01 (applied only to matrix-shaped parameters, not norms).
On top of that: cosine decay to 1e-5 with 3% warmup, fused AdamW, gradient clipping at 1.0.

**Monitoring.** Periodic evaluation runs greedy decoding on the GSM8K test split, tracking pass@1 and the fraction of
generations that produce no parseable answer plus sample generations logged to TensorBoard.

**Result: 46.5% pass@1, 69.1% pass@8** on the GSM8K test split.

The large gap between `pass@1` and `pass@8` shows the SFT model can often produce a correct solution but doesn't rank it
as the most likely one. This suggests that doing some RL should sharpen the distribution and improve the `pass@1`.

### Stage 2: GRPO ([HF logs](https://huggingface.co/chibo/minillm/tensorboard))

GRPO implemented from scratch on top of the batched inference engine - no TRL, no vLLM.

**Rollout phase.** Each iteration samples batches of 16 GSM8K training prompts and
generates a group of 8 rollouts per prompt (top-p 0.95, temperature 1.0). Rollouts
are graded by executing the generated Python solution:

- **+1** - the program runs and its answer matches the reference
- **−1** - no numeric answer (crash, timeout, or syntactically invalid program)
- **0** - runs fine, wrong answer

Truncated generations are dropped, and groups where every rollout got the same reward are skipped entirely (otherwise
their advantages would all be zero). Because the "useful rollout" yield varies a lot between batches, the loop keeps
sampling prompt batches until at least 512 usable rollouts are collected, so every gradient update sees a consistent
amount of signal regardless of how the sampler did.

**Advantages.** Group-relative and mean-centered only - not divided by the group std. With ternary rewards,
std-normalization would systematically underweight {−1, +1} groups (highest variance = most informative disagreement),
so I used the [Dr. GRPO](https://arxiv.org/pdf/2503.20783)-style unnormalized advantage here.

**Update phase.** Each rollout batch is reused for 3 gradient updates with PPO-style ratio clipping (eps=0.1).
A KL penalty (beta=0.004, [k3 estimator](http://joschu.net/blog/kl-approx.html) `exp(r) − r − 1`)
anchors the policy to a frozen copy of the SFT model. The loss is normalized by a constant rather than per-sequence
length, this is the Dr. GRPO fix that avoids biasing the objective toward long incorrect completions.

**Monitoring.** TensorBoard tracks reward composition (correct / wrong / broken program), truncation ratio, mean output
length, per-token KL, the fraction of clipped ratios, and grad norm - plus sample generations logged at every eval so
degenerate outputs are visible immediately, not just as a metrics dip.

**Results**
| Stage | pass@1 | pass@8 |
| ------ | --------- | --------- |
| SFT | 46.5% | 69.1% |
| + GRPO | **53.9%** | **70.2%** |

GRPO improves pass@1 by +7.4 points but pass@8 by only +1.1, which is expected. RL mostly sharpens the distribution -
shifting probability mass onto solutions the SFT model could already sample - rather than adding new capability. This
matches the pass@k dynamics reported in the recent RLVR literature (e.g. [Yue et al.
2025](https://arxiv.org/abs/2504.13837)). Training was stopped when pass@1 plateaued.

### Comparison with the TinyGSM paper

The TinyGSM paper reports a pass@1 of **63.1%** for its 125M model. That number isn't directly comparable to minillm's
53.9%, because of the following differences:

|              | TinyGSM paper (125M)                                                      | minillm (152M)                                           |
| ------------ | ------------------------------------------------------------------------- | -------------------------------------------------------- |
| Base model   | Phi-1.5 architecture, pretrained on the same curated data as Phi-1.5 1.3B | Llama-style, pretrained from scratch on a FineWeb sample |
| Tokenizer    | Phi-1.5 tokenizer                                                         | GPT-2                                                    |
| SFT training | 20k steps                                                                 | 11.5k steps                                              |

Additionally, it looks like the dataset published by the TinyGSM authors to
[HuggingFace](https://huggingface.co/datasets/TinyGSM/TinyGSM) is different from the one described in the paper (the number
of samples differs: 11.8M vs 12.3M).

The paper's pretraining ablation (Table 2) shows that finetuning on TinyGSM from a random init (i.e., without the Phi-1.5
pretraining) performs substantially worse (pass@1 53.1%), so the pretraining difference alone accounts for a large share of the gap.

Natural next steps for closing the gap could be:

1. Pretrain on code as well (e.g. use the [Smollm-corpus](https://huggingface.co/datasets/HuggingFaceTB/smollm-corpus) dataset that mixes `FineWeb` with `python-edu`)
2. Spend more compute on finetuning
